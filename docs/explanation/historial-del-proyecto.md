# Historial del proyecto

Cómo evolucionó `ignite-brief` desde el MVP inicial hasta el estado actual. Sirve para entender por qué ciertas cosas están como están, no como changelog operativo del día a día.

- **2026-09-13 — V1 (MVP):** primera versión, a partir de `Brief_Campaña_ignite_ops_Taquion_ES.pdf` (plantilla genérica de brief de campaña). Ver `specs/005-brief-campana-ignite.md` en el repo hermano `SDD-TAQUION` para el detalle completo de esa primera versión.
- **2026-09-13 — Deploy real:** conectado a Vercel vía import de Git (proyecto `brief-campana-ignite-aw3s`, auto-deploy en cada push a `master`), con Deployment Protection desactivado para que sea público. URL: [brief-campana-ignite-aw3s.vercel.app](https://brief-campana-ignite-aw3s.vercel.app).
- **2026-09-13 — Automatización n8n (opcional):** se armó el workflow que genera un Google Doc/PDF por cada brief nuevo, disparado por un Database Webhook de Supabase (no depende del frontend — ver [por qué](./decisiones-de-arquitectura.md#por-qué-el-disparador-de-la-automatización-es-supabase-y-no-el-formulario)). Quedó pendiente de credenciales/plantilla real para activarse en ese momento.
- **2026-09-14 — Deploy paralelo en Netlify:** Taquión estandariza en Netlify para herramientas nuevas, así que se sumó como segunda plataforma en paralelo a Vercel (mismo repo, mismo Supabase) — [merry-mooncake-95f231.netlify.app](https://merry-mooncake-95f231.netlify.app). Igual que en Vercel, el proyecto tenía "Private by default" (Project visibility) activado por defecto — se cambió a Public en *Project configuration → Visitor access* para que el link fuera realmente accesible.
- **2026-09-14 — Supabase conectado en producción:** se creó el proyecto `Brief-campañas-taquion` en Supabase (org `Marketing-Taquion-IGNITE`) y se lo vinculó al repo de GitHub (integración nativa de Supabase, pensada para futuras migraciones — al momento de este historial el schema se sigue cargando a mano en el SQL Editor). Se cargaron `SUPABASE_URL` y `SUPABASE_ANON_KEY` (formato `sb_publishable_...`, el que reemplaza a la `anon key` clásica) como variables de entorno en Vercel y Netlify, y se verificó el flujo completo: alta desde el formulario → visible en el panel → mismo dato en ambas plataformas (comparten la misma base). La fila de prueba se borró después de verificar.
- **2026-09-14 — Campos de presupuesto y duración:** se sumaron `presupuesto` (radios $5M/$12M/$20M) y `duracion_fechas` (calendario propio para marcar días sueltos, no un rango). Migración aplicada en producción vía `alter table ... add column if not exists`, probada end-to-end contra el Supabase real.
- **2026-09-14 — Subida de archivos en "Recursos clave":** se agregó un botón real de subida (antes solo se podían pegar links). Los archivos van al bucket público `briefs-recursos` (tope 15 MB por archivo) y su link se suma automáticamente a `recursos_clave` junto con los enlaces tipeados a mano. Supabase marcó de entrada una advertencia de seguridad ("Clients can list all files in this bucket") por una política de `select` que se había agregado — se sacó esa política porque era innecesaria (ver [por qué](./decisiones-de-arquitectura.md#storage-sin-política-de-lectura-select)) y se verificó que el acceso a archivos existentes no se rompió.

## Qué queda como posible próximo paso

Estos puntos aparecen mencionados en el proyecto como opciones futuras, no como trabajo pendiente confirmado — ver [Decisiones de arquitectura](./decisiones-de-arquitectura.md) para el contexto de cada uno:

- Agregar autenticación (contraseña compartida, o Supabase Auth + RLS por usuario) si en algún momento se decide que el link ya no puede ser público.
- Reactivar el envío por email cuando se genera un documento nuevo (agregar un nodo Gmail al workflow de n8n), si el equipo lo pide.
